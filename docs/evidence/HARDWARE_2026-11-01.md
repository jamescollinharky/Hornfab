## Decision

**Consider GPU rental before buying another computer.** Keep the laptop for development, geometry, and result inspection. A short rental pilot is a much smaller commitment than choosing a new machine from an unverified performance model.

There are two different capacity targets:

1. **Current wall-coarse 12 kHz mesh:** 8,625 dofs / 16,909 triangles. A 24 GB RTX 4090 is a reasonable first test; 32 GB RTX 5090 and 48 GB L40S are comparison options. None is proven to complete the contracted sweep. More VRAM does not by itself diagnose error 719.
2. **Whole-surface 12 kHz sizing under the existing validator:** the fixed T2 seed first passes among the tested sizes at **33,959 dofs / 67,245 triangles**, not 25-35k triangles. The pinned standard CUDA path's dense arrays alone imply **85.410 GiB of simultaneously required storage before additional workspace** (source-derived below). Thus the listed 24/32/48/80 GB tiers cannot run that exact mesh/path. **H200 141 GB is the first listed discrete tier worth testing for this target; fit and runtime remain unmeasured.**

Consequently, buying a 24/32 GB desktop specifically to finish a defensible full-wall 12 kHz campaign would be premature. It could be useful for coarse screening, but that is a different fidelity commitment. A Mac or AMD unified-memory computer is also an unvalidated backend purchase, not an established substitute.

The smallest configuration proven to run the contracted full sweep, and the cheapest configuration proven to finish overnight, are both **unknown**. The recommendations above identify the next economical tests, not proven winners.

## The memory diagnosis is less certain than the handoff says

A flat near-capacity `nvidia-smi` reading is not proof of constant live workspace. CUDA.jl caches allocations, distinguishes live versus reserved storage, and can report high device use after arrays become unreachable. Its documented `JULIA_CUDA_MEMORY_POOL=none`, soft/hard limits, and pool diagnostics are potential isolated A/B measurements, not switches measured here. Validate behavior against the installed CUDA.jl version before use. [CUDA.jl memory management](https://cuda.juliagpu.org/stable/usage/memory/).

Error 719 is a device launch failure; NVIDIA documents invalid pointers and out-of-bounds access among its possible causes. It is not the allocation-OOM error. The observed near-full device and repeat failure support investigating memory pressure, but do not uniquely prove it. [NVIDIA CUDA error definitions](https://docs.nvidia.com/cuda/archive/12.0.1/cuda-driver-api/group__CUDA__TYPES.html).

Before concluding a larger card solves the crash, a pilot must complete the exact sweep and check output shapes/finiteness/reciprocity. A failure with substantial free memory would shift investigation toward the kernel/driver/path. No Windows timeout registry setting was changed.

### Static CUDA memory accounting, not a measured peak

The pinned four-operator CUDA assembler allocates two complex64 N-by-E operators and two N-by-N operators (`julia/src/BeatEngineCudaAssembly.jl:70-78,151-156`). DP0 count equals E (`BeatEngineCore.jl:437`). The CUDA identity cache stores dense complex64 N-by-N and N-by-E arrays (`BeatEngineCore.jl:1185-1187,1417-1423`; driver initializes it at `BeatEngineDriver.jl:1667`). The channel solve retains those operators/caches while constructing a further N-by-N LHS (`BeatEngineCore.jl:1527-1536`). Therefore:

`operators = 16*N*E + 16*N^2 bytes`

`operators + dense identity cache + one LHS = 24*N*E + 32*N^2 bytes`

| Measured mesh N / E | One complex64 N-by-N matrix GiB | Four operators GiB | Operators + identities + LHS GiB |
|---|---:|---:|---:|
| 8,625 / 16,909 | 0.554 | 3.282 | 5.477 |
| 17,211 / 33,938 | 2.207 | 13.118 | 21.884 |
| 33,959 / 67,245 | 8.592 | 51.212 | 85.410 |
| 38,819 / 76,919 | 11.227 | 66.948 | 111.650 |

These are source-derived storage amounts, **not baseline/peak VRAM observations**. Assembly also creates separate real/imaginary buffers before complex materialization; LU, geometry, correction caches, context and allocation overlap add cost. Exact peak requires measurement. Even the four operators alone exceed a 48 GB card at the first globally valid mesh; the identities and LHS also exclude 80 GB. Multiple 24 GB cards do not pool memory for one candidate in this engine.

## Scaling law and existing solver options

No controlled factorial benchmark over E, N, C and F exists here. The historical 69 successes vary geometry over a narrow N range on one GPU; the larger samples have different frequency grids/start states, and the long sweep failed. Fitting a transferable bandwidth/FP32/VRAM performance law to those would be false precision.

Source-supported model, with coefficients **unfitted**:

`T_candidate = T_geometry_mesh + T_start + sum_f[A(E,N,k_f) + C*S_dense(N,k_f) + C*Field(E,P,k_f) + request_overhead] + T_inner(F) + T_write`

Regular assembly launches over E-squared pairs and symmetry images (`CudaAssembly.jl:30-36,82-135`); it includes quadrature and transcendental work, not just a memory copy. CUDA dense LU adds cubic work in N and quadratic storage. Per-channel LHS construction/refactorization repeats; operator assembly itself is shared per frequency. Channels must be genuinely driven tags, not duplicate amplitudes; the current MEH has two, so a four-channel probe needs a valid separate fixture. These are algorithmic dependencies, not fitted hardware laws.

| Engine path at approved pin | Method/reuse | Available option and limitation |
|---|---|---|
| Standard CUDA, including measured MEH sizes | Fixed dense direct solve, fresh LHS/solve per channel | Current production path. `BLAB_BEAT_DENSE_SOLVE=gmres` does not route it to GMRES. |
| Fused CUDA | Dense LU, exactly one channel | `HORNLAB_BEAT_FUSED_BM_CUDA=1`; driver refuses MEH multi-channel (`Driver:1848-1854`). |
| CPU / Metal fused | Cost-model LU or GMRES; LU shared across channels | `BLAB_BEAT_DENSE_SOLVE=auto|lu|gmres`; GMRES may fall back to LU (`DenseSolve.jl:315-324,968-1005`). |
| CPU / Metal standard | Shared CPU factorization per frequency | `BLAB_BEAT_FUSED_BM=0` disables fusion. Metal assembles GPU, solves CPU (`Driver:1972-1979`). |
| ROCm standard | GPU dense solve per channel | Source exists; this project's MEH correctness/performance untested. |

CUDA matrices are single precision; double is CPU-only. Near correction is not a general MEH performance switch: standard accelerator routes refuse it; fused CUDA's restrictions and single-channel refusal prevent using it here. No tolerances were changed. No option comparison was timed in this pass. A future reuse optimization would be a solver-fork change requiring the FORKS validation ladder, not a setting already available in this CUDA path.

These are required rates, not achieved speeds. Reserve time for verification by using `screen_hours = 8 - setup_hours - verify_hours - retry_margin` and required total rate `80/screen_hours`. GPUs must each fit a candidate; lanes do not split its dense matrices.

**Cheapest initial concurrency route to consider:** two separate single-GPU rental machines, one existing 40-candidate brief on each, with separate local checkout/runtime/registry/cache/dataset/run roots. This uses the existing independent briefs rather than implementing within-generation parallelism. It is untested operational deployment, but does not require shared-host device cleanup changes. Each brief must itself finish in the available night; two machines cannot solve a too-slow individual brief. Do not share a live worker registry or canonical dataset filesystem between them.

**A shared-box 1/2/4/8-lane change is not one line.** Exact implementation surfaces:

1. `search/cma.py:265-285,313-342`: coordinator retains CMA, budget, cache accounting, failure streak, seed and replay; dispatch indexed candidates, collect in ask order, retain complete-generation `tell(X,F)` barrier. Preserve duplicate handling and interrupted-run replay.
2. `search/evaluate.py:741-799,1315-1385`: evaluator currently mutates memo/counters/files and persists dataset/NDJSON; extract a child computation stage returning isolated artifacts. Parent alone publishes records in deterministic order. `dataset/store.py:34-35` explicitly assumes one process writer; its thread lock is insufficient.
3. `solve/cache.py:144-165`: duplicate candidates cannot concurrently replace the same cache entry. Use private staging and parent-only publication/deduplication.
4. `search/gpulock.py:134-181`: replace the global lock/owner bypass with device-UUID and machine-scoped ownership. Handle multi-host filesystem/PID identity correctly; do not bypass a live lock.
5. `solve/worker.py:243-280,384-430`: multiple hosts are presently treated as stale and cleanup can kill all hosts. Track and stop only a lane's owned host tree. Isolate `HORNLAB_BEAT_WORKER_DIR` and set `CUDA_VISIBLE_DEVICES` before imports/host start; BEAT's keyed environment omits the latter (`worker_client.py:59-69`). Scope VRAM monitoring and recovery per device too.

Risk: host adoption/termination across lanes, corrupt shared writes, changed CMA order/budget semantics, and partial-resume errors. Test these offline, then prove independent device assignment and noninterference on real GPUs. Owner's multi-GPU investigation request authorizes this design study; no production multi-GPU change or global rule rewrite was made.

## CPU configuration

The measured mesh builds above take about 4-10 seconds on one laptop process, and the historical network optimizer takes 6.582 seconds on its specific 12-frequency case. Its cost at 41 frequencies is not established. CPU time is not a fixed 6.6-second constant across grids. The stored CUDA diagnostics show 24 BLAS threads; that is not evidence 24 is optimal or required.

For a single-GPU pilot, use the provider's included CPU/RAM first, log effective Julia/BLAS thread settings and host RSS, and avoid oversubscribing. For lanes, benchmark disjoint physical-core sets and explicit Julia/BLAS/OpenMP caps, including child-process affinity and NUMA placement. `mesh/step_build.py:347-377` has an in-process gmsh lock; use processes for separate meshing lanes. No evidence decides whether a 16-core desktop beats a 32-core server once all lanes run. The larger full-wall solve also invalidates the handoff's unsupported blanket claim that 64 GB system RAM is always enough; size from measured host peak RSS plus per-lane runtime needs.
